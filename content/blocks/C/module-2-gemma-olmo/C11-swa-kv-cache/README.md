# KV-cache для sliding window: кольцевой буфер

## Зачем это нужно

В C05 KV-cache рос на один токен за шаг: на контексте 128K он хранит 128K ключей в каждом слое.
Но sliding-слою (C07) из всей истории нужны только последние $W$ токенов — всё, что старше, уже
никогда не попадёт в его окно. Значит, кеш sliding-слоя можно держать **фиксированного размера**:
$W$ ячеек, и новый токен перезаписывает самый старый. Это кольцевой буфер (rolling buffer cache —
так его называют авторы Mistral 7B).

Для модели с одними sliding-слоями (Mistral 7B, окно 4096) память под кеш перестаёт расти после
4096 токенов. Для Gemma 3 27B (5 sliding : 1 full, окно 1024) на 128K токенов кеш в bf16 занимает
≈ 10.4 ГиБ вместо ≈ 62 ГиБ, если бы все слои были full: почти всё место теперь занимают 10 full-слоёв.

## Что поменялось относительно C05

| | C05 (`KVCache`) | C11 (`RingKVCache`) |
|---|---|---|
| размер | растёт: $S$ токенов | фиксирован: $W$ ячеек |
| где лежит токен $p$ | в позиции $p$ тензора | в ячейке $p \bmod W$ |
| порядок ключей в тензоре | хронологический | после переполнения — «по кругу», не по порядку |
| что возвращает `update` | весь кеш `[B, H_kv, S, D]` | буфер **до записи** + новые токены, и их **позиции** |
| маска | `tril(ones(T, S), S − T)` по индексам | по абсолютным позициям: $0 \le p_q - p_k < W$, ключ существует |

Порядок ключей в тензоре не важен: attention — это взвешенная сумма по ключам, и от перестановки
ключей (вместе с их значениями и масками) результат не меняется. RoPE уже применён к ключам при
записи, так что «где лежит» ключ на результат тоже не влияет. Важно только правильно построить маску —
**по позициям**, а не по индексам.

Почему `update` возвращает буфер **до** записи плюс новые токены, а не буфер после записи: при
куске из $T > 1$ токенов запись новых может вытеснить ключи, которые ещё нужны первым запросам
куска. Пример: $W = 4$, в буфере позиции 2..5, пришли 6, 7, 8. Запросу 6 нужны ключи 3..6, но
после записи 6, 7, 8 в буфере останутся только 5..8. Поэтому attention получает 4 старые ячейки + 3
новых ключа, а маска отсеивает лишнее.

## Формула

Новые токены на позициях $p = s, …, s + T - 1$, где $s$ = `cache.seq_len` до обновления.
Ключи для attention: $K = [\text{buf}_K;\ k_{\text{new}}]$ с позициями $\pi = [\text{buf}_\text{pos};\ s..s{+}T{-}1]$
(в пустых ячейках $\pi = -1$).

$$
M_{i,j} = \begin{cases} 0, & \pi_j \ge 0 \ \text{и}\ 0 \le p_i - \pi_j < W \\ -\infty, & \text{иначе}\end{cases}
$$

Запись: для последних $\min(T, W)$ новых токенов `buf[p % W] ← (k_p, v_p)`, `buf_pos[p % W] ← p`.

Память модели со смесью слоёв (2 — это K и V):

$$
\text{bytes} = 2 \cdot \Big(\sum_{\text{sliding}} \min(S, W) + \sum_{\text{full}} S\Big) \cdot H_{kv} \cdot D \cdot B \cdot \text{bytes/elem}
$$

## Формы тензоров

```shapes
x [B, T, C] — только новые токены
q_pos [T] — arange(s, s + T), где s = cache.seq_len ДО update
fork
> q_proj, RoPE по q_pos
q [B, H, T, D]
branch
> k_proj (RoPE по q_pos), v_proj
k, v [B, H_kv, T, D]
> cache.update(k, v)
K, V [B, H_kv, W + T, D] — буфер до записи + новые
k_pos [W + T] — −1 = пустая ячейка
join repeat_kv → [B, H, W + T, D], q·Kᵀ/√D
scores [B, H, T, W + T] — + маска по позициям
> softmax, @ V, o_proj
out [B, T, C]

## буфер после записи
cache.k, cache.v [B, H_kv, W, D]
cache.pos [W]
```

Пример: $W = 4$, после 10 токенов по одному `cache.pos = [8, 9, 6, 7]` — токен $p$ в ячейке $p \bmod 4$.

## Критерии готовности

- токен $p$ лежит в ячейке $p \bmod W$, буфер всегда `[B, H_kv, W, D]`, при куске длиннее окна
  остаются последние $W$;
- `update` возвращает все ключи, нужные новым запросам, с верными позициями;
- без кеша — SWA из C07; по одному токену, prefill + decode, куски 5 + 3 + 6 + 2, $W = 1$ и $W > T$ —
  ровно как полный прогон;
- после 60 шагов буфер всё ещё $W$ ячеек;
- память: Gemma 3 27B на 128K — 10.4 ГиБ; Mistral 7B — 512 МиБ и на 4K, и на 32K.
