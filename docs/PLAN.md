# План: LLM Arch Lab

Работа разбита на фазы. **Одна фаза — одна сессия Claude Code** (большие фазы делятся на
подфазы a/b/c). Между фазами `/clear`. Состояние передаётся через `docs/PROGRESS.md`.

Порядок выбран так, чтобы как можно раньше получить работающий сквозной сценарий
(задача → тесты → конспект), а потом наращивать контент.

---

## Фаза 0 — Каркас и формат задач

**Цель:** репозиторий, пакет, CLI, раннер тестов, формат задач, одна демо-задача от начала до
конца, но пока без UI.

## Блок A — Фундамент: от производной до своего GPT

**Зачем:** блок C начинается с готовой GPT-2 и предполагает, что backprop, оптимизаторы, токенизация и
attention уже понятны. Блок A закрывает этот фундамент с нуля, чтобы курс можно было проходить без
предварительной подготовки. Блок необязательный: кто знает основы, сразу идёт в C. Заканчивается
блок своей маленькой GPT, обученной на CPU. Это мост к C00.

**Общие правила блока:**
- Autograd (модуль 1) пишем на чистом Python и скалярах, torch используем только как эталон в тестах. Дальше
  берём `torch.Tensor` без `nn`/`optim` в реализуемой части: `nn.Linear`, `F.cross_entropy` и `torch.optim`
  служат эталонами для сравнения.
- Обучение в тестах — сотни шагов на игрушечных данных, < 2 с. Инварианты: лосс падает, получается
  переобучиться на одном батче, градиент совпадает с конечными разностями и с `torch.autograd`.
- Данные лежат в репозитории и написаны нами (маленький корпус собственного текста, ≤ 50 КБ). Ничего не скачиваем.
- Идеи micrograd/minbpe (Karpathy) не копируем: код и тексты пишем свои, ссылки на источники даём в «Чтение».

## Блок B — Энкодеры: от Transformer к ModernBERT и эмбеддингам

**Зачем:** блок C — только декодеры. Но классификация, разметка, извлечение ответов, эмбеддинги для поиска
и reranking в проде держатся на энкодерах, а исходный Transformer был энкодер-декодером. Блок B показывает
вторую ветку эволюции: Transformer (2017) → BERT → RoBERTa / DistilBERT → T5 → ModernBERT → Sentence-BERT.
Блок необязательный и не нужен для C. Для старта достаточно A16–A17 (attention, блок), multi-head
объясняется в B01 заново.

**Общие правила блока:**
- Реализации на `torch.nn` без готовых слоёв трансформера: `nn.MultiheadAttention`, `nn.Transformer*`,
  `F.scaled_dot_product_attention` служат эталонами в тестах и запрещены в коде пользователя.
- Имена параметров — как в Hugging Face (`BertModel`, `T5Model`, `ModernBertModel`), где задача сверяется с
  `transformers` на случайных весах. Тесты с реальными весами — `@pytest.mark.weights`.
- Обучение в тестах — игрушечные синтетические данные, < 2 с; проекты обучаются ~1 мин на CPU вне тестов.
- Гиперпараметры реальных моделей — только из `config.json` на HF или статей, со ссылкой.

## Блок D — После предобучения: дообучение, выравнивание, быстрый инференс

**Зачем:** блоки A–C заканчиваются предобученной моделью: она продолжает текст, но не отвечает на вопросы, не
следует формату и медленно генерирует. Блок D проходит путь от такой модели до ассистента в проде: SFT на
диалогах → дешёвое дообучение (LoRA) и сжатие (квантизация) → выравнивание по предпочтениям (reward model, DPO) и
RL с проверяемой наградой (GRPO) → быстрый инференс (батчи, speculative decoding, paged KV-cache, continuous
batching). Блок не обязательный в смысле A/B, но строится на C: нужны модель Llama-типа (C06), KV-cache (C05) и
сэмплирование (C25a), а из A — цикл обучения (A09). В задачах это `depends_on` на C-задачи; кто шёл только по C,
может начинать.

**Общие правила блока:**
- Модель — `llmlab.core.model.Model` (Фаза 8) в игрушечных конфигах (`llama-like` и уменьшенные копии, d_model ≤ 64)
  или мини-GPT из A18. Своих архитектур в D нет: блок про то, что делают с готовой моделью.
- Готовые библиотеки — только эталоны в тестах: `peft`, `trl`, `bitsandbytes`, `vllm` в зависимости не добавляем;
  где можно, сверяемся с формулой из статьи и с `transformers` (например, `apply_chat_template`). Если эталон
  требует новой зависимости — только в extra `weights` и только для `@pytest.mark.weights`.
- Обучение в тестах — десятки шагов на синтетических задачах (арифметика, копирование, форматы), < 2 с. Проекты
  учатся несколько минут на CPU вне тестов; результаты эксперимента в README — с командой воспроизведения.
- Вероятностные механизмы (сэмплирование, speculative decoding, GRPO-группы) проверяются двумя способами:
  детерминированно при `temperature = 0` / фиксированном генераторе и статистически (распределение по
  ≥ 10⁴ сэмплам на маленьком словаре против точного, χ²-порог с запасом, фиксированный сид).
- Реальные веса: SmolLM2-135M и Qwen3-0.6B уже поддержаны `core/hf.py` (C24/C25) — weights-тесты и проекты
  берут их. Гиперпараметры методов (ранги и α LoRA, β DPO, ε клиппинга, размер группы GRPO, размер блока
  квантизации) — только из статей или конфигов, со ссылкой; иначе TODO-verify.
- Данные — синтетические, генерируются кодом в репозитории (как B06). Готовые датасеты инструкций не скачиваем.
