## TL;DR

Sliding-слою нужны только последние $W$ токенов, поэтому его KV-cache — кольцевой буфер из $W$
ячеек: токен $p$ пишется в ячейку $p \bmod W$, вытесняя самый старый. Память слоя перестаёт расти с
контекстом (Mistral 7B: 512 МиБ на любом контексте ≥ 4K; Gemma 3 27B на 128K: 10.4 ГиБ вместо 62).
После переполнения ключи в буфере идут не по порядку — это не мешает (attention инвариантен к
перестановке ключей, RoPE уже применён), но маску надо строить по **абсолютным позициям** ключей.
`update` возвращает буфер до записи + новые токены, чтобы кусок из нескольких токенов не потерял
нужные ключи.

## Формула

$$\text{slot}(p) = p \bmod W,\qquad M_{ij} = 0 \iff \pi_j \ge 0 \wedge 0 \le p_i - \pi_j < W$$

$$\text{bytes} = 2\,\big(\textstyle\sum_\text{sliding}\min(S, W) + \sum_\text{full} S\big)\,H_{kv} D\,B\,\text{bytes/elem}$$

## Формы тензоров

```
buf k, v [B,H_kv,W,D], pos [W];  update → K, V [B,H_kv,W+T,D], k_pos [W+T]
scores [B,H,T,W+T] + маска по (q_pos, k_pos) → out [B,T,C]
```

## Что поменялось относительно C05

Кеш фиксированного размера вместо растущего, запись по модулю $W$, и маска по позициям ключей
вместо сдвинутого треугольника по индексам. Позиции запросов, как и в C05, начинаются с
`cache.seq_len` до обновления.
