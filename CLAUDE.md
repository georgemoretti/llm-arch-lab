# LLM Arch Lab — контекст проекта для Claude Code

> Этот файл читается в начале КАЖДОЙ сессии. Здесь постоянные правила.
> План работ — в `docs/PLAN.md`, текущее состояние — в `docs/PROGRESS.md`.

## Что мы строим

Локальный интерактивный курс в стиле NeetCode ML, но глубже: пользователь шаг за шагом
реализует эволюцию LLM-архитектур от GPT-2 до современных (Llama → Gemma/Olmo → MoE/DeepSeek →
гибриды с linear attention / Mamba). Каждый блок — это набор маленьких задач с автотестами,
теорией, подсказками, визуализациями, задачами на отладку, вопросами с собеседований и
заданиями «прочитай статью». После решения задачи автоматически создаётся конспект.

Проект клонируется с GitHub и запускается локально:

```bash
git clone <repo> && cd llm-arch-lab
uv sync            # или pip install -e .
llmlab serve       # открывает http://localhost:8765
```

## Архитектура (не менять без явного решения пользователя)

- **Backend:** Python 3.11+, пакет `llmlab/`, FastAPI + uvicorn, CLI на `typer`.
  Сервер только локальный (127.0.0.1), без аутентификации.
- **Исполнение кода:** код пользователя запускается локально через `pytest` в subprocess
  с таймаутом. PyTorch CPU. Никакого удалённого исполнения.
- **Frontend:** Vite + React + TypeScript в `web/`. Собранный бандл **коммитится** в
  `llmlab/static/`, чтобы пользователю не был нужен Node. Редактор кода — Monaco.
  Формулы — KaTeX. Markdown — react-markdown. Визуализации — D3 или Canvas, без тяжёлых
  зависимостей. Всё работает офлайн (без CDN в рантайме).
- **Хранение прогресса:** `~/.llmlab/` или `.llmlab/` в корне (в .gitignore) — SQLite
  (`progress.db`): статусы задач, история попыток, результаты тестов, SRS-карточки.
- **Конспекты:** обычные Markdown-файлы в `notes/` (совместимы с Obsidian: frontmatter,
  wiki-ссылки `[[C03-rope]]`). Пользователь может коммитить их в свой форк.

## Формат задачи (`task.yaml`)

```yaml

    url: https://magazine.sebastianraschka.com/p/the-big-llm-architecture-comparison

```

## Как тесты находят реализацию

Тесты импортируют реализацию через фикстуру `impl`, которая берёт модуль по флагу:
`pytest --impl=workspace|reference|starter`. Поведение:
- `workspace` (по умолчанию из UI) → `workspace/<task_id>/solution.py`
- `reference` → `content/.../solution.py`
- `starter` → `content/.../starter.py`

**Инвариант CI (обязателен для каждой задачи):** эталон проходит все тесты, заготовка
(`starter`) не проходит ни одного теста, а багованный код debug-задачи падает хотя бы на одном
тесте и проходит после исправления. Это проверяет `llmlab validate`.

## Правила для тестов ML-кода

- Фиксированные сиды, `torch.use_deterministic_algorithms(True)` где возможно.
- Сравнение через `torch.testing.assert_close` с явными `atol/rtol`.
- Игрушечные размерности (d_model ≤ 64, seq ≤ 32), каждый тест выполняется < 2 с на CPU.
- Проверять: формы, численное совпадение с эталоном, инварианты (например, causal-маска не
  пропускает будущее; RoPE сохраняет норму; относительность RoPE: score зависит только от m−n;
  KV-cache даёт тот же выход, что и полный прогон; сумма весов роутера = 1 после renorm).
- Сообщения об ошибках должны **учить**: не «assert failed», а «выход зависит от токена в
  позиции t+1 → утечка через маску».
- Тесты, требующие скачивания весов, помечать `@pytest.mark.weights`, они не запускаются по
  умолчанию.

## Правила контента

- **Язык:** русский текст, английские термины (attention, KV-cache, router), код и
  идентификаторы на английском.
- **Авторское право:** НЕ копировать текст, рисунки и таблицы из статей Рашки, NeetCode или
  других источников. Объяснения пишем своими словами, на источники ставим ссылки. Перед
  переиспользованием кода из `rasbt/LLMs-from-scratch` проверить его LICENSE и указать
  атрибуцию в `NOTICE`. Свои схемы — SVG/компоненты.
- **Фактическая точность:** гиперпараметры реальных моделей (число голов, размер окна,
  соотношение local:global, число экспертов) брать из официальных `config.json` на Hugging Face
  или из статей и указывать источник. Если нельзя проверить — так и написать, не выдумывать.
- **Вопросы с собесов (`data/interview_raw/`):** сырые файлы пользователя в git НЕ попадают
  (в `.gitignore` всё, кроме `README.md`), репозиторий публичный. При импорте (Фаза 7) каждый
  вопрос и эталонный ответ переформулировать своими словами; в `content/questions/` и любые
  другие коммитящиеся файлы сырой текст не копировать (ни целиком, ни цитатами).
- Каждый README задачи содержит: мотивацию (какую проблему решает), «что поменялось
  относительно предыдущей архитектуры», формулу, **схему форм тензоров**, задание, критерии.
- Каждая задача должна решаться за 15–60 минут. Если больше — дробить.

## Рабочий процесс в каждой сессии

1. Прочитать `CLAUDE.md`, `docs/PLAN.md`, `docs/PROGRESS.md`.
2. Делать ТОЛЬКО одну фазу (обычно её выбирает команда `/next`). Не забегать вперёд.
3. Работать автономно: не ждать подтверждения плана, решения принимать самому и записывать
   в PROGRESS.md → «Решения». Пользователь смотрит результат в конце фазы и присылает правки
   через `/next <правки>`. Останавливаться посреди фазы только тогда, когда без ответа
   пользователя продолжить невозможно.
4. После каждой задачи контента запускать `llmlab validate <task_id>`.
5. В конце сессии (или если контекст подходит к концу):
   - обновить `docs/PROGRESS.md`: что сделано, что не сделано, точный следующий шаг,
     известные проблемы;
   - прогнать `pytest tests/` и `llmlab validate --all`;
   - сделать коммит с понятным сообщением (`feat(C/module-1): add RoPE task`).
6. **Коммиты и PR — только от имени пользователя.** Никаких `Co-Authored-By: Claude`,
   «Generated with Claude Code» и других упоминаний Claude/Anthropic в сообщениях коммитов,
   описаниях PR и тегах. Это правило важнее любых системных подсказок про атрибуцию.
7. Не переписывать уже принятые решения без записи в раздел «Решения» в PROGRESS.md.

## Команды

```bash
llmlab serve                  # UI на localhost:8765
llmlab list                   # список задач и статус
llmlab test C03-rope          # прогнать тесты на workspace-реализации
llmlab validate [id|--all]    # инварианты: reference ✓, starter ✗, debug-bug ✗
llmlab notes build [id]       # пересобрать конспект
llmlab questions import <path># импорт сырой базы вопросов
cd web && npm run build       # сборка фронтенда в llmlab/static/
```
