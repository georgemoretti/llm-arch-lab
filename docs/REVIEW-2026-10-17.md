### Результаты мутационного тестирования

1271 мутант: **1123 убито (88 %)**, 148 выжило. Из выживших:

- **80** — в коде, который заготовка даёт готовым: конструкторы (`bias=False`), сигнатуры со значениями по
  умолчанию, данный `generate` в C06. Пользователь этот код не пишет.
- **~60** — эквивалентные мутации:
  - `dim=-2` → `2` у тензоров фиксированного ранга;
  - позиции с 1 вместо 0 без кеша — RoPE зависит только от m − n, выход тот же;
  - `+eps` → `−eps` при положительном знаменателе;
  - `.float()` на входе, который уже fp32;
  - `argsort(stable=False)` — порядок внутри эксперта не важен;

  - `shape[-2]` ≡ `shape[-1]` при T = S (C18) или батче 4000 ≥ k (C25).

### Находки

**1 (P1). Задачу можно сдать импортом эталона.**

```python
# workspace/C01-rmsnorm/solution.py
from llmlab.core.llama import rms_norm, RMSNorm
```

Это проходит C01 13/13. Так же работает для C13 (`llmlab.core.moe`), C21 (`llmlab.core.efficient`) и любой
задачи, чей эталон лежит в `llmlab/core/` — то есть почти для всех, включая C24/C25 через `llmlab.core.hf`.
Задача засчитывается решённой, создаётся конспект, открывается ячейка таблицы.

Для самостоятельного курса это не уязвимость, но:
- статус «решено» и конспект ничего не гарантируют;
- такой «ответ» легко получить случайно — автодополнение IDE подсказывает `llmlab.core.*`.

Предложение: в фикстуре `impl` после импорта проверять, что объекты из `task.entrypoint` (и имена из задания)
определены в самом файле решения — `obj.__module__ == impl.__name__`. Для чужих объектов тест падает с текстом
«`rms_norm` импортирована из `llmlab.core.llama` — это эталон; реализуй её в solution.py». Импорт **других** деталей
из `core` (как задумано в C05+) этим не запрещается.

**2 (P1). C14, `test_route_with_bias`: перенормировка не проверяется.** Выбраны эксперты 1 и 3 с весами
0.8 и 0.2 — их сумма уже 1.0. Поэтому решения без деления на сумму и даже с умножением на сумму (мутант
`/`→`*`) проходят. Других тестов на перенормировку в `route_with_bias` нет. Предложение: взять scores, у которых
сумма выбранных ≠ 1 (например, 0.6 и 0.2 → 0.75 / 0.25), и оставить диагноз «веса из scores + bias».

**3 (P2). `assert_close` без явных допусков — 43 вызова** (CLAUDE.md: «сравнение через `assert_close` с явными
`atol/rtol`»). Задачи (+d — и в debug-копии): C03 (+d), C04 (+d), C05 (+d), C11, C12 (+d), C14 (+d), C15, C16 (+d), C17, C18, C19, C20 (+d),
C21 (+d), C23. Работает это верно — у fp32 строгие допуски по умолчанию, и почти везде сравниваются точные
копии. Но правило нарушено, а при переходе на bf16 / другую библиотеку поведение молча изменится. Предложение:
для «точных» сравнений (кеш, перестановки) — `atol=0, rtol=0`, для численных — явные 1e-5 / 1e-6.

**4 (P2). C16: ветка `k_rope` в `LatentCache.update` не проверяется.** README C16 требует реализовать
`update(c, k_rope=None)`, но тесты C16 вызывают его только без `k_rope` (выжили 4 мутанта строк 26–27). C16b
импортирует `LatentCache` из `llmlab.core.mla`, а не из решения пользователя, так что ошибка в этой ветке не
всплывёт нигде. Предложение: тест в C16 с двумя вызовами `update(c, k_rope)` и проверкой конкатенации по dim=1 —
или убрать `k_rope` из задания C16 и объяснить в C16b.

**10 (P3). Непроверенные граничные случаи.**
- C25 `sample_next`: при `before >= p` против `> p` поведение отличается, только если сумма вероятностей ровно
  равна p — такого теста нет. Нет теста и на `top_k > V` (`min(top_k, V)`).
- C24 `config_from_hf`: значения по умолчанию для отсутствующих ключей (`tie_word_embeddings`, `rope_theta`,
  `layer_norm_epsilon`) не проверяются — все три тестовых config.json задают их явно. Значение по умолчанию
  `tie_word_embeddings` особенно коварно: в `PretrainedConfig` оно `True`, а в `LlamaConfig` / `Qwen3Config` —
  `False`.

### Находки

**5 (P2). Нет раздела «Формула»** в README C24 и C25 (TASK_FORMAT §2.2, правило CLAUDE.md). Для C24 формулы по
сути нет — это задача на сопоставление имён, — поэтому стоит либо добавить раздел «Сопоставление» и оговорить
исключение в TASK_FORMAT, либо дать хотя бы формулу Conv1D → Linear (Wᵀ). В C25 формула сэмплирования есть в
`summary.md`, но не в README.

**6 (P2). Оценки времени paper-задач:** C-P2 — 75 мин, C-P3 — 90, C-P4 — 90 (правило: 15–60). Это чтение 3–5
статей. Варианты: разбить каждую на две paper-задачи или явно оговорить в CLAUDE.md / TASK_FORMAT, что правило
15–60 относится к задачам с кодом.

**7 (P2). Симптомы, которые выдают баг.**
- C16d: «кеш `forward` занимает в H(d + d_v)/r раз больше памяти, чем должен» прямо говорит, что в кеш кладутся
  K/V вместо латента. Мягче было бы так: «после длинного prefill память растёт быстрее, чем у GQA с тем же числом
  голов» — и пусть отношение посчитает сам пользователь.
- C01d: «с увеличенным eps расхождение видно и на обычном масштабе» сильно подсказывает, где искать. Допустимо,
  но можно убрать вторую половину фразы.

**12 (P3). C25 на 55 минут — оптимистично.** Нужно написать четыре функции. `load_safetensors` (шарды) и
`generate` с eos — короткие. `load_pretrained` — это meta-устройство, `assign=True` и восстановление связанных
весов. `sample_next` — temperature, top-k и top-p. Предложение: вынести сэмплирование в отдельную задачу
C25a (~25 мин), а C25 оставить про загрузку и генерацию.
