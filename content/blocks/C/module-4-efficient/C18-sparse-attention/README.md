# Sparse attention в стиле DSA: индексатор и top-k ключей

## Зачем это нужно

На длинном контексте основная стоимость декодера — attention: каждый новый токен сравнивается со
**всеми** $S$ предыдущими, на весь текст выходит $O(T^2)$. Sliding window (C07) решает это грубо: запрос
видит только последние $W$ токенов, а что было раньше — только через стопку слоёв. Окно фиксировано и
не зависит от содержания: важное определение из начала документа выпадет из окна так же, как мусор.

DeepSeek Sparse Attention (DSA, DeepSeek-V3.2-Exp, 2025) выбирает ключи **по содержанию**. Каждый запрос
сначала прогоняет по всем прошлым токенам очень дешёвый «оценщик» — **lightning indexer**, — а затем
полноценное attention считается только по $k$ лучшим ключам (у DeepSeek-V3.2 $k = 2048$). Основное
attention стоит $O(T \cdot k)$ вместо $O(T^2)$; индексатор по-прежнему квадратичен, но он в разы дешевле:
мало маленьких голов, один ключ на токен, ReLU вместо softmax (у DeepSeek ещё и FP8).

Важно: KV-cache при этом **не уменьшается** — чтобы выбирать, нужно хранить все ключи. DSA экономит
вычисления, а не память (в отличие от MLA, C16).

## Что поменялось относительно C07

| | C07 (sliding window) | C18 (DSA) |
|---|---|---|
| какие ключи видит запрос $t$ | фиксированно: $t - W < s \le t$ | $k$ ключей с наибольшей оценкой индексатора среди $s \le t$ |
| зависит от содержания | нет | да, маска своя у каждого запроса |
| маска | одна на весь батч, известна заранее | считается на лету: $[B, T, S]$, общая для всех голов |
| что добавилось | — | `LightningIndexer`: $H_I$ голов размера $d_I$, общий ключ, веса голов $w_{t,h}$ |
| при $k \ge T$ / $W \ge T$ | обычное causal attention | обычное causal attention |

## Формула

Индексатор для запроса $t$ и ключа $s \le t$:

$$
I_{t,s} = \sum_{h=1}^{H_I} w_{t,h} \cdot \operatorname{ReLU}\!\left(q^{I}_{t,h} \cdot k^{I}_{s}\right),
\qquad
q^I_{t,h} = W^{(h)}_{qI} x_t,\quad k^I_s = W_{kI} x_s,\quad w_{t,h} = (W_w x_t)_h
$$

В задаче оценка дополнительно делится на $\sqrt{d_I}$ и $\sqrt{H_I}$ (как в эталонном коде DeepSeek:
`softmax_scale` и `n_heads ** -0.5`); для top-k общий множитель неважен, но держит числа в разумном масштабе.

Выбор и attention:

$$
\mathcal{S}_t = \operatorname{top\text{-}k}_{s \le t}\, I_{t,s},
\qquad
o_t = \sum_{s \in \mathcal{S}_t} \operatorname{softmax}_{s \in \mathcal{S}_t}\!\left(\frac{q_t^\top k_s}{\sqrt d}\right) v_s
$$

Если допустимых ключей меньше $k$ (первые $k$ токенов), берутся все: $|\mathcal{S}_t| = \min(k, t + 1)$.

## Формы тензоров

```shapes
x [B, T, C]

## LightningIndexer: дешёвая оценка, какие ключи важны
fork
> q_proj → view
q_I [B, T, H_I, d_I]
branch
> k_proj — одна «голова» ключей
k_I [B, T, d_I]
join q_I·k_I / √d_I — einsum "bthd,bsd->bths"
[B, T, H_I, S]
> ReLU, Σ_h w·(…) — w = weights_proj(x)/√H_I [B, T, H_I], einsum "bth,bths->bts"
> будущее (s > t) → −inf
index_scores [B, T, S]

## topk_mask
> topk(min(k, S), dim=-1) — индексы [B, T, k]
> scatter → bool
> & isfinite(scores) — убрать −inf, которые topk добрал в коротких строках
keep [B, T, S]

## DSAttention
q, k, v [B, H, T, d]
> q·kᵀ/√d
scores [B, H, T, S]
> masked_fill(~keep[:, None]) — маска общая для всех H голов
> softmax, @ v
out [B, H, T, d]
> → [B, T, C] → o_proj
axis H_I:heads = головы индексатора
axis d_I = размер головы индексатора
axis S = позиции ключей
axis k = сколько ключей оставляем каждому запросу
```

## Задание

В `solution.py` (рабочая копия в `workspace/C18-sparse-attention/`) реализуй:

1. `LightningIndexer.forward(x)` → оценки `[B, T, T]` с `−inf` для будущих ключей;
2. `topk_mask(index_scores, top_k)` → булева маска `[B, T, S]`;
3. `sparse_attention(q, k, v, keep)` → `[B, H, T, d]`;
4. `DSAttention.forward(x, return_mask=False)` → выход `[B, T, C]` (и маска, если `return_mask`).

Конструкторы даны, имена параметров не меняй. Позиционного кодирования нет. Упрощения относительно
DeepSeek: нет RoPE в индексаторе и в основном attention, нет LayerNorm на ключе индексатора, преобразования
Адамара и FP8; основное attention — обычное MHA, а не MLA (C16).

**Как учат индексатор.** Через `topk` градиент не проходит, поэтому у индексатора свой лосс. В отчёте
DeepSeek-V3.2 сначала идёт короткий «прогрев» с плотным attention: индексатор учат повторять распределение
внимания основной модели (KL-дивергенция между ними), затем модель дообучают уже в разреженном режиме. В этой
задаче обучения нет — только прямой проход.

## Реальные числа

DeepSeek-V3.2-Exp (`config.json`): `index_n_heads = 64`, `index_head_dim = 128`, `index_topk = 2048`.
Остальная архитектура — как у DeepSeek-V3 (MLA, 128 голов, `kv_lora_rank = 512`, MoE 256 + 1 эксперт).
Значит, на контексте 128K каждый запрос считает полное attention лишь по 2048 ключам — 1.6 % контекста.

## Критерии готовности

- оценки индексатора совпадают с формулой $\sum_h w \cdot \operatorname{ReLU}(q \cdot k)$, будущее = $-\infty$ и не
  влияет на прошлые строки;
- `topk_mask`: в строке $t$ ровно $\min(k, t+1)$ ключей, все из прошлого, и это ключи с наибольшими оценками;
  при $k \ge S$ маска совпадает с causal;
- `sparse_attention` совпадает с маскированным softmax-attention и не зависит от невыбранных ключей;
- `DSAttention` при $k \ge T$ совпадает с обычным causal MHA, при малом $k$ — с attention по выбранным
  индексатором ключам, и не утекает в будущее.
