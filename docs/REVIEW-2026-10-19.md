## 2. Качество тестов

### Метод

Мутационное тестирование эталонов (`solution.py`) всех задач implement / debug / project. Мутации по AST: замена
арифметических операторов и сравнений, ±1 и ×2 у констант, `and ↔ or`, удаление унарного минуса, `.detach()` /
`.float()` / `.clamp()`, смена `dim` / `keepdim`, `tril ↔ triu`, `sum ↔ mean`, обрезка срезов. До 60 мутантов на
задачу в A/B и до 40 в C. Каждый мутант запускался отдельным процессом:
`pytest test_task.py --impl-path=<мутант>`. В каждой задаче есть контрольный «мутант» — немутированный эталон; все
контроли прошли тесты, значит стенд корректен. После прогона все выжившие мутанты разобраны вручную.

### Результаты

| блок | задачи (без debug-копий и проектов) | debug-копии | проекты |
|---|---|---|---|
| A | 471 / 541 убито — **87 %** | 219 / 237 — 92 % | A18: 21 / 60 |
| B | 652 / 777 — **84 %** | 316 / 379 — 83 % | B06: 14 / 60, B20: 17 / 60 |
| C | 827 / 938 — **88 %** | 466 / 541 — 86 % | C24 + C25: 51 / 63 |

В блоке C доля убитых мутантов та же, что на прошлом ревью (88 %). Новых дыр нет: выживают эквивалентные мутанты
(`dim=1` на 2D, `transpose(2, -1)` на 4D), значения по умолчанию (`eps`, `theta`, `temperature`) и готовые
конструкторы (`bias=False` в C09/C18, инициализация роутера C12).

Debug-задачи используют тесты родительской задачи, поэтому повторяют её результат. В проектах A18, B06 и B20
выживает большинство мутантов, но они меняют готовый код: CLI `main()`, вывод, параметры эксперимента и
`number_to_words`. Тестировать его не обязательно.

Разбор выживших мутантов в задачах A/B:

- **Эквивалентные** (около 60 %): `transpose(2, -1)` на 4D-тензоре, `dim=1` вместо `-1` на 2D, `x >= 0` против `x > 0`
  в производной ReLU у тензоров (`A04`, без точных нулей), `.float()` на fp32, `n <= max_exact` в бакетах T5 (оба
  варианта дают один бакет), `searchsorted(cu_seqlens[0:])` в B17 (сдвиг номера текста на 1 не влияет на равенство).
- **Значения по умолчанию** (около 30 %): тесты всегда передают `eps`, `gain`, `lr`, `weight_decay`, `temperature`,
  `prob`, `norm_first` явно, поэтому смена значения по умолчанию незаметна. Почти все такие сигнатуры даны в
  заготовке готовыми, ученик их не пишет. Для учебного курса это приемлемо.
- **Готовый код** (`generate` в A10, `_is_punctuation` в B07, инициализация в A15/A18/B02, обрезка в B15): см. находку 8.
- **Реальные дыры** в коде, который пишет ученик: находки 2–5.

Реалистичная ошибка в `clip_grad_norm_` (A08) — масштабировать градиент всегда, без условия `coef < 1` — тестами
ловится. Выжил только искусственный мутант `coef < 0.5`, поэтому отдельной находкой это не считается.

### Находка 1 (P2). `assert_close` без явных допусков в A и B

Правило CLAUDE.md требует явные `atol/rtol`. В блоке C все 43 вызова исправили после прошлого ревью, но в A и B
снова **31 вызов в 14 задачах**: A15, A16, A16d, A17, B01, B01d, B02, B03, B04, B04d, B05, B05d, B11, B11d. Многие из
них сравнивают bool-маски или точные перестановки, где подходят `atol=0, rtol=0`. Регресс случился потому, что
`llmlab validate` это не проверяет.
**Предложение:** расставить допуски по схеме из C (данные — `0/0`, численные — `1e-6/1e-5`). В `validate` (или в
тест платформы) добавить AST-проверку: `assert_close` в `test_task.py` без `atol` и `rtol` → error.

### Находка 2 (P2). A01: производная ReLU проверяется только вдали от нуля

В заготовке написано: «Производная в нуле — 0 (так договорились и PyTorch, и тесты)». Но тестов в нуле нет: ReLU
проверяется только при x = 1.3 и x = −1.3. Выживают мутанты `self.data >= 0`, `self.data > 1` и `self.data > -1`, то
есть неверная производная на всём интервале (−1, 1).
**Предложение:** добавить в `UNARY` точки x = 0 (значение 0, производная 0), x = 0.4 и x = −0.4. Либо убрать из
заготовки слова про тесты, но точки ±0.4 всё равно нужны.

### Находка 3 (P2). A09: «валидация после последнего шага» не проверяется

README и докстринг требуют валидацию «после шагов, где `(step + 1) % eval_every == 0`, **и после последнего**». В
тесте `steps = 120` и `eval_every = 40`, поэтому последний шаг 119 и так попадает в плановую валидацию. Решение без
отдельной проверки последнего шага проходит.
**Предложение:** взять `steps = 110` и ожидать `[39, 79, 109]` (отдельный тест или второй прогон).

### Находка 4 (P3). B09: квадратный батч и слово 0

`_batch(B=256, T=256)`. Поэтому `torch.rand(input_ids.shape[1], n_words)` вместо `shape[0]` (перепутаны оси батча и
времени) проходит. В режиме `word_ids` проходит и `word_ids >= 1`: слово 0 никогда не маскируется. Статистический тест
«≈ 15 % слов» такое не замечает.
**Предложение:** взять неквадратный батч (например, 192 × 256) и добавить детерминированную проверку: при `prob = 1`
выбраны все слова, включая 0.

### Находка 5 (P3). B08: граница обрезки пары

Выживает мутант `len(a) + len(b) < max_tokens` вместо `<=`: пара, которая влезает впритык, обрезается на токен.
Также выживает `n_short >= half` вместо `>`.
**Предложение:** добавить случай `len(a) + len(b) == max_tokens` (без изменений) и случай `n_short == half`.
